# Review — plan-v1.md

## 1. Coverage of the frozen acceptance criteria

The plan has a sound central policy direction: `plan-v1.md:43-59` narrows `DocumentViewer` to the four fields the current predicates actually read, and current `src/lib/api/v1/documentAccess.ts:61-76` confirms that the Internal-room check remains first and that no call site needs a semantic rewrite. `plan-v1.md:61-93` also gives preview and welcome one pure `computePerimeter` path. The lookup, preview, welcome, flag, documentation, demo, and mandatory-gate surfaces are all named.

**1.1 — Carry the inviter-confirmed phase through the real invitation and acceptance lifecycle.** Frozen A7/A9/B7 and the brief require a proposed phase that the inviter may change and explicitly confirm before send (`spec-v2.md:109-114`, `brief.md:19-21`). The plan accepts `phase` only in the preview request (`plan-v1.md:113-133`), asserts no persistence (`plan-v1.md:17,272-274`), and does not change the invitation API/RPC. Current evidence proves that the invitation cannot preserve an override: `src/app/api/v1/invites/route.ts:60-67,183-192` has no phase input/RPC argument, while `supabase/migrations/20260804160000_invite_safeguard_2fa.sql:707-719` grants and audits phase `0` unconditionally. Revise the plan to carry the confirmed phase through form state, the preflight snapshot, send-time validation/authorization, the pending invite, acceptance, and the grant audit. Because that requires durable pending-invite state, name a forward migration, safe backfill/check/constraint, acceptance-RPC change, and rollback/containment; add tests proving an override is previewed, persisted, reauthorized at send, and granted exactly as confirmed. If a surface has a frozen non-applicable phase (for example an internal Gate 0 seat), say so explicitly and test that boundary rather than silently dropping A9.

**1.2 — Deliver the live preview in Gate 0 before its queued invitation is sent.** The approved experience makes the preview available before invitation send (`brief.md:21,38-46`; `spec-v2.md:78-81`), but M12 mounts only M8 in Gate 0 (`plan-v1.md:33-35`) and M6 requires an already-resolved deal (`plan-v1.md:107-121`). Current Gate 0 queues locally because the deal does not exist, creates the deal, and then immediately posts every queued invitation (`src/components/wizard/inviteQueue.ts:1-6`; `src/components/wizard/Gate0Wizard.tsx:594-598,841-883`). Revise M6/M9/M12 and the Gate 0 state transition so an authorized user can open a server-authoritative preview for the exact queued proposal before send, with explicit human confirmation and without inventing a third invitation flow. Name how the server authorizes and computes a pre-deal proposal, or where a post-create/pre-send confirmation boundary lives, and test the whole Gate 0 path.

## 2. Scope and reuse of existing product surfaces

The intended scope is otherwise disciplined. M11-M14 reuse Team, Gate 0, Member Drawer, and the existing force-dynamic external deal home; M2 reuses the document wall and destination policy; M5 reuses invitation-domain helpers; M10 stays inside Deal/Data Room/Team. The plan introduces no crawler, sanctions/enrichment dependency, chatbot, autonomous grant, new destination, task system, or persisted preview. The persistence required by finding 1.1 is not adjacent scope: it is the minimum durable state needed to make the frozen confirmed phase survive from send to acceptance, and Q12 expressly requires a migration and rollback when that need is discovered.

No additional scope blocker beyond 1.1 and 1.2 is raised in this section. Their revisions must continue to reuse the two existing invitation flows, preflight gate, existing external shell, central predicates, and current send/accept lifecycle.

## 3. Data lifecycle, flags, stale inputs, and audit semantics

The plan correctly makes lookup and preview read-only (`plan-v1.md:93,153-155,193`), gates both routes before authorization, keeps the welcome in the existing flag-on branch, and preserves send-time authorization conceptually. The local request-key comparison plus abort is the right race primitive for prospective lookup/preview.

**3.1 — Specify fail-closed handling for every authoritative read; an error must never become an empty or partial answer.** `plan-v1.md:132-141,163-178` names company, party, document, user, seat, and pending-invite reads, but does not distinguish query failure from a missing row. UI copy for a generic 5xx (`plan-v1.md:239-240`) is not a server design. Revise M5, M6, and M10 so every policy/scoping read checks its database error and returns or renders an opaque unavailable result; a document query error must not compute `total: 0`, and a failed user/invite/domain query must not emit a partial warning set, company match, or recommendation. Preserve `404` only for a proven missing resource. Add injected-read-error tests for lookup, both preview modes, and welcome recomputation, including assertions of no audit/write side effects.

**3.2 — Bind existing-member previews to the member identity and preview kind.** M6 accepts `{kind:"member", userId, phase}` (`plan-v1.md:119-120`), but `PreviewBoundInputs` contains only lookup inputs plus role/company-role/phase (`plan-v1.md:197-203`); it has no `kind` or `userId`, and its surface union excludes Member Drawer. A late response for member A can therefore share a key with member B, or the proposed type cannot represent M13 at all. Replace it with discriminated prospective/member bound-input types whose member key includes canonical deal ID, target `userId`, proposed phase, and member surface. Test member changes, phase changes, out-of-order responses, failure, and the whole-company drawer path so no preview survives a target change.

## 4. Edge cases and test quality

The planned pure parity matrix, inaccessible-metadata assertions, role/phase permutations, zero state, welcome archetypes, seeded demo, and mandatory lint/type/test/build gates are useful. The D8 table, however, assigns obligations to files that cannot exercise the required behavior.

**4.1 — Expand the test plan so all sixteen D8 obligations and the affected cross-cutting invariants are actually verified.** In particular:

1. D8.4 must run the **same normalized request** twice against states differing only in the hidden user/seat/invite fact; deep-equality against a different “unknown address” cannot succeed because the response includes `normalizedEmail` and domain-derived fields (`plan-v1.md:184-190,247-250`). Include cross-company and cross-tenant ordinary actors plus cross-tenant CCO/admin actors.
2. D8.5-D8.6 require parent-surface integration tests for Gate 0 and `InviteModal`, proving failure/supersession withdraw real form prefills and cannot bypass the existing preflight confirmation. Merely rendering `SmartLookupCard` with two surface props (`plan-v1.md:252-254`) does not prove either invitation flow retained the gate.
3. D8.11 requires a client `PerimeterPreview`/parent integration test for unavailable and out-of-order responses, including Member Drawer target changes. An API test cannot prove that a stale response never renders (`plan-v1.md:249-253`).
4. D8.15 says **every affected surface**. The proposed flag test mentions two routes and deal home only (`plan-v1.md:255`); add Gate 0, Team invite, Member Drawer, and welcome UI parity plus route non-disclosure before auth.
5. Add verification for A11/D3 secret absence, B9/D4 audit neutrality and unchanged send/accept/grant/view/download behavior, Box/fallback non-regression, D5 keyboard/AT/narrow-width behavior, and the migration/acceptance behavior required by 1.1. These are frozen plan-rubric obligations even where they are not separate D8 list entries.

## 5. Technical security and consistency with existing authorization

The member phase-raise preview correctly chooses `userIsDealMd`, the same predicate used by the current PATCH (`plan-v1.md:123-128`; `src/app/api/v1/deals/[dealId]/members/[userId]/route.ts:81-97`). The `DocumentSubject` structural refactor also leaves current predicate ordering intact. Three security blockers remain.

**5.1 — Make prospective preview/lookup authorization equal to a feasible invitation, not merely `userCanInvite`.** The plan calls `userCanInvite` and then trusts validated request role/company-role/phase (`plan-v1.md:123-133,159-170`). Current code explicitly says `userCanInvite` does **not** enforce invitation shape (`src/lib/api/v1/access.ts:292-303`); the send route separately enforces director privilege, external/internal role allowlists, and party-derived seller/buyer role (`src/app/api/v1/invites/route.ts:110-172`). It also transactionally enforces actor/company/deal tenant coherence in `create_invite` (`supabase/migrations/20260804160000_invite_safeguard_2fa.sql:357-379`). This matters immediately because `userCanInvite` lets a firm admin short-circuit before any tenant check (`src/lib/api/v1/access.ts:304-327`), so M6 could reveal cross-tenant document counts for a proposal the actor cannot send. Extract or define one server-side proposal-feasibility path shared by lookup, preview, preflight/send, covering canonical tenant coherence, actor authority, company-role privilege/coercion, company type, party-derived deal role, and phase bounds. Re-run it at send time. Add negative tests for cross-tenant admin UUID probes, external own-company constraints, impossible role/company-role combinations, changed party relationship, and lost authority.

**5.2 — Scope company matches and existing-user facts before constructing the flat warning response.** A flat warning array is a good output discipline, but it does not make its inputs authorized. M5 searches verified domains across the actor's whole tenant (`plan-v1.md:161-170`), which is broader than A3's actor scope and can name an unrelated company to an external inviter. Its A17 rule also proposes calling `userCanViewCompany` (`plan-v1.md:174-180`), while the current helper returns true for every CCO/admin without checking that the target company shares the actor's tenant (`src/lib/api/v1/access.ts:154-169`). Define the actor-scoped candidate-company set before matching, require explicit actor/user tenant equality for the overseer branch, and fail closed on every scope-read error. Resolve the response-schema contradiction between “flat array of ids” and the object example (`plan-v1.md:180,184-190`) with one canonical, fixed-order schema whose reason copy is static and carries no metadata. Add the same-input alternate-state indistinguishability tests described in 4.1.

**5.3 — Correct the unknown-room fail-closed claim.** `plan-v1.md:237` says `userCanSeeDocument` denies an unknown room, but the current predicate only specially handles `internal` and otherwise evaluates classification/phase (`src/lib/api/v1/documentAccess.ts:61-76`). The database currently constrains persisted rooms to `internal|deal` (`supabase/migrations/20260731120000_onboarding_invites.sql:122-125`), yet M2 deliberately types a gate row's room as arbitrary `string` (`plan-v1.md:64-72`). Narrow and validate the decoded row as `DocumentRoom` and make any unexpected value an unavailable server result, or deliberately change and parity-test the shared real-access predicate. Do not leave a false security guarantee in the plan or a pure helper that treats unexpected values as reachable.
