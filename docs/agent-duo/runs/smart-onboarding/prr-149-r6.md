## 4.1 — the predicate decided before it finished reading

The report is correct, and it is worse than it reads: the tenant coherence I
added in round 5 is what sharpened the oracle. That read returns early when the
company cannot be resolved, which is exactly and only the sentinel case, so
absence became cheaper than a hidden row in the very change that closed the
cross-tenant leak.

I also accept the framing I disputed twice. A19 enumerates response properties,
but the condition it protects is "you cannot tell hidden from absent", and a
predicate that answers "no such row" faster than "a row you cannot see" tells
you. Reading the enumeration as exhaustive was lawyering.

`userCanManageInvite` now gathers before it decides (`access.ts:444-485`). Four
reads issue unconditionally in one batch — the actor, the invited company, the
deal, and the actor's seat on that deal — and every rule is evaluated in memory
afterwards. Where there is no real row the read looks up an id that cannot
exist (`NO_SUCH_ROW`, `access.ts:6`) rather than being skipped. The rules
themselves moved into four shared predicates (`access.ts:11-26`) so the
constant-shape path and the branching helpers state each rule once; the
branching helpers were rewired to call them, and their read schedules are
unchanged.

With work constant inside the predicate, the route's dual-shape construction
became unnecessary: one call with the real shape now suffices
(`lookup/route.ts:340-352`), and the comment that used to concede the residual
is gone because there is no longer a residual to concede.

Coverage, which the review correctly said could not have caught this: the A19
harness recorded table names and ignored filter arguments, so a sentinel id
read the same canned row as a real one. It now records `table(filter columns)`
for every read (`tests/lookup-indistinguishable.test.ts:34-62`), and the
schedule test compares three worlds — no invitation, an invitation attached to
nothing, an invitation attached to a deal — asserting identical schedules and
naming the four reads that must be present
(`tests/lookup-indistinguishable.test.ts:250-292`). Mutation: restore the
conditional deal read, which is the historical shape; the schedule test fails.
Reverted, 8 passed. All 67 existing authority verdicts are unchanged by the
refactor.

## 3.1 — the seat comes from acceptance, and the factor is real

**Preinstalled membership.** Correct: a fixture written before acceptance would
have agreed with the ending whatever acceptance did. Tables may now be supplied
as thunks, and `accept_invite` creates the membership from the stored
invitation (`tests/onboarding-e2e.test.ts:166-183`). The walk reads the
perimeter *before* acceptance and asserts the invitee has no seat
(`tests/onboarding-e2e.test.ts:435-444`), so the seat that appears later is
produced by the transition rather than by the fixture.

**The second factor.** Also correct: `/api/v1/auth/mfa/complete` only validates
an event and writes a row, so posting to it directly proved nothing about
authentication. The walk now renders the real two-factor page
(`tests/onboarding-e2e.test.ts:484-544`): it challenges the factor, verifies
the code and confirms AAL2 before recording, with the challenge id and code
that reached `mfa.verify` asserted rather than assumed, and it continues to the
destination only after that. Then the real `requireApiUser` — the guard every
protected route runs — refuses the invitee at aal1 and admits them at aal2
(`tests/onboarding-e2e.test.ts:546-573`).

Mutations, all caught and reverted: make the deal read conditional again; make
the session aal2 where the walk expects refusal, proving the refusal is about
assurance and not something incidental; and stop the verification from raising
assurance, proving the client will not record or navigate without it.

No production behaviour changed for D4. The 2FA flow is walked, not modified.
