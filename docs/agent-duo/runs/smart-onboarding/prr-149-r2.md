## 1.1 — bound inputs and withdrawal. Fixed

`companyId` and `surface` are now bound inputs of the card and of the request.
Domain matching and `classifyInviteDomain` run against **the selected company's**
verified domains when a company is selected, so "this domain does not match the
company record" is a claim about the company on screen rather than whichever
candidate happened to match. An out-of-scope `companyId` is ignored, not trusted.

Withdrawal now withdraws. `appliedRef` records what the recommendation put into
the form; a lost result reverts exactly those values, and only if the inviter
has not since changed them.

Two defects surfaced while fixing this, both found by running the test:

- **An infinite render loop.** Reverting `companyId` re-keyed the lookup, which
  emitted null, which reverted again. Cause was treating "no result yet" and
  "result lost" as the same thing. `onResult` now receives the status, and only
  `unavailable` or a changed address counts as lost.
- **Withdrawal restored the recommendation.** A repeat delivery for the same
  address re-captured "what was there before" — by then that was the
  recommended company itself. Preserved across repeat deliveries.

The round-1 test asserted only that the card went stale, and you were right that
it passed for the wrong reason: it passed against a parent that kept the values.
It now asserts the company and phase come back out, and that a company the
inviter chose themselves is left alone.

## 1.2 — welcome brief offered an action the send route refuses. Fixed

`canInviteTeammate` was `isExternal && companyRole === 'director'`, a role-name
shortcut. Real `userCanInvite` also requires the director's company be a current
party. A seated director of a removed party would have been offered an action
that 403s. `PerimeterContext` now carries a decided boolean; the member and
viewer paths call the real predicate, and a failed read is `unavailable` rather
than a guess in either direction.

## 4.1 — A19 timing oracle. Fixed, and a round-1 claim retracted

The schedule is now fixed: the same queries run and the same predicates are
evaluated whether or not the rows exist. A sentinel that matches nothing keeps
the query shape identical when there is nothing to look up. Existence changes
only what is concluded.

**Retraction.** In an interim note I claimed a residual difference of one read
that could not be removed. That was wrong. It was my own fixture draining a
mocked `users` queue differently between the two worlds, so the authority
predicate got a null actor in one of them and took a shorter path. With the
fixture corrected the schedules are identical for all three classes — user,
seat, and invitation — and the tests now assert that.

**Limit, stated plainly.** I could not get a mutation (making the seat read
conditional on existence again) to fail these tests, so they demonstrate the
property holds in the shipped code but are weaker evidence than the other
guards in this PR, where I confirmed the failing mutation. I would rather say
that than imply a strength I did not establish.

## Factual correction

`prr-149.md` and commit `59805e0` say the authority block runs "under the
advisory lock it already took". It does not. The **`FOR SHARE` row locks**,
taken before the derivation and held to commit, are what protect it; the email
advisory lock comes afterward (`invite_phase.sql:191`). The protection is real,
my description of it was wrong.
