## 4.1 — authority no longer authorized against the wrong resource. Fixed.

Committed in `f6cbca6` before this round's work. The replacement gate
`pending.company_id === actor.company_id` asked whether the actor owned the
company, which is a different question than whether they may manage the
invitation.

`userCanManageInvite` branches on whether the invitation is attached to a deal,
so a sentinel that changes that shape changes the branch. Both shapes are now
evaluated on every call and the real value selects. Work stays constant whether
or not a pending invitation exists, and the verdict is about the invitation
actually being disclosed.

My first attempt used `pending?.deal_id ?? NO_ROW`, which turned a legitimately
null deal into a fake deal id and sent a company-scoped invitation down the deal
branch. The indistinguishability suite caught it. Mutation: `mayManage = true`
-> 2 failed; reverted -> 8 passed.

## 1.2 — the collapse is gone from the predicates themselves. Fixed.

Round 3 was right that the split was incomplete: `userCanInviteChecked` returned
`'unreadable'` for its own reads but called `canManageDealMembers` and
`canManageCompanyMembers`, which collapse their read errors to `false`.

Rather than wrap them, the `Checked` variant is now THE implementation and the
boolean is a one-line view over it:

```ts
const canManageCompanyMembers = async (...) =>
  (await canManageCompanyMembersChecked(...)) === true;
```

Added `canManageCompanyMembersChecked`, `userIsDealMdChecked`,
`canManageDealMembersChecked`. Every existing caller keeps deny-on-error byte
for byte, because that is right for enforcement; only the perimeter path, which
shows the answer to a person, maps `'unreadable'` to `unavailable`.

Two actor reads moved `single` -> `maybeSingle`. Under `single` a missing row is
itself an error, which would have reported an absent actor as unreadable instead
of false — a real difference, since the first is "we could not tell" and the
second is "there is no such actor".

Tests assert each read failure twice against the same stub: `'unreadable'` from
the `Checked` form, still `false` from the boolean. Mutations: drop
`if (membershipError)` -> deal test failed; drop `if (actorError)` -> company
test failed; reverted -> 21 passed.

**Disclosed, not covered.** The composed path — a nested unreadable becoming
`unavailable` at the perimeter — is still verified by inspection of two lines
(`=== 'unreadable' ? null` in `realInvitationAuthority`, `if (canInvite === null)`
in `perimeterForMember`). Reaching it from a test means sequencing five reads
through `getDocumentViewer`, and a stub positional enough to do that would
assert its own shape more than the code. Raising it rather than claiming B10 is
fully automated.

## 1.1 — the D8.6 tests are back, and they were not flaky. Fixed.

They were racing a real cascade, not failing intermittently. A recommendation
that pre-fills the company changes one of `SmartLookupCard`'s own bound inputs,
so the card re-keys and looks up again; a test that touched a bound input before
that second cycle landed saw the in-flight delivery re-apply what the change had
just withdrawn.

Test discipline only, no source change: `lookupSettled()` waits for two
consecutive polls at `ready` with no new lookup between them. Both tests are
restored — a company change withdraws the applied phase, and an inviter-typed
phase survives the next recommendation, which exercises `phaseTouched` on both
the withdrawal and the apply side. The withdrawal case holds the next lookup
`PENDING` rather than failing it, so it cannot pass through
`status === 'unavailable'` with the key comparison deleted.

Mutations: drop `|| currentKey !== applied.key` -> company-change test failed;
drop the `!phaseTouched` apply guard -> typed-phase test failed; reverted -> 9
passed, five consecutive green runs.

## Gate 0 preview — the wizard was wrong, not the route. Fixed.

Surfaced by round 3 as an extra. The route requires `dealId` and `dealRole` to
be both present or both absent; `assessProposal` returns invalid for a deal role
with no deal, and the `invites` table CHECKs the same pairing. The 400 was the
rule, so the fix is `dealRole={null}` in `Gate0Wizard` — the role is applied at
send, once the deal exists. One test whose stub applies the route's real pairing
rule and asserts the request body directly. Mutation: restore
`dealRole={inviteRole}` -> 1 failed.

## 4.2 — one walk instead of two probes. Fixed, and it found a defect.

The old test stopped at send and then manufactured an already-active viewer.
Everything D7 asks for after send — acceptance, the code challenge, the terms,
the seat, the brief — was absent or proven separately in SQL, so the two halves
could agree while sharing nothing.

`tests/onboarding-e2e.test.ts` now runs one invitation from the typed address to
the rendered `WelcomeBrief`. Added after send: the challenge refused with a wrong
code and passed with the right one; acceptance refused before verification (409)
and refused again without the terms (400, with the `accept_invite` call count
held flat, so the refusal is provably before the RPC); acceptance with the terms,
asserting the `ATTEST` row is written before the grant; then the seat's perimeter
and the brief.

What makes it a walk rather than a sequence: a three-field invitation store
(`id`, `phase`, `verified`) backs `create_invite`, `verify_invite_challenge` and
`accept_invite` on both the admin and the session client, and the invitee's
`deal_memberships` fixture reads `invite.row.phase`. The phase the MD confirms
is the phase the RPC carries, is the phase the seat holds, is the count the brief
prints. The store re-implements no authority; the grant and its audit remain
SQL's to prove (`supabase/tests/invite_phase_accept.sql`).

Mutations: `p_phase: 0` in send -> failed at the brief, which is the continuity
proof; drop the `invite_not_verified` mapping -> failed; drop the TOS gate ->
failed; `ATTEST` -> `VIEW` -> failed; reverted -> 2 passed.

### The front door, and the defect behind it

D7 starts at a typed address, so the walk starts at the real `InviteModal` with
`fetch` answered by the real handlers. Both existing invite-surface tests stub
literal bodies, so nothing until now proved the UI reads the shape the handler
actually returns.

It did not. **The Team modal never identified a counterparty company.** The
select opens on the advisory bank, the modal passed that untouched default to
lookup, and lookup reads a selected company as "does THIS address belong to THAT
company" — so `alex@target.dev` returned `companyMatch: null`,
`recommendation: null`, warning `unverified_domain`, and nothing pre-filled. The
runbook has claimed since 2026-08-08 that the card "names the company behind the
domain when a verified domain the actor can see matches it". On Team that was
not true.

Fix, one line: `companyId={companyTouched ? companyId || null : null}`. The
component already keeps `companyTouched` for exactly this distinction and sets
it only from the inviter's own `onChange` — a recommendation pre-filling the
select deliberately does not. Untouched is not a choice, so lookup gets the
question the route documents for it: "before any choice — which candidate
company it belongs to, if any". A deliberate mismatch still warns, because
touching the select still sends it.

Side effect worth naming: the bound input no longer changes when a
recommendation pre-fills the company, so the self-chasing second lookup from
finding 1.1 does not occur on this surface.

Mutation: revert the line -> the front-door step failed; restored -> 2 passed.
