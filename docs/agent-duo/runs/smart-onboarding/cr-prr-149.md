# Review — prr-149.md

## 1. Coverage of the frozen criteria

The PR implements the three requested surfaces behind `platform_onboarding`: smart lookup in Gate 0 and Team, proposal/member perimeter previews, and a recomputed external welcome brief. It also carries the confirmed invitation phase through `create_invite` and `accept_invite`. The actual head reviewed is `c3e94deb3fb7d3712d6572322a1bdc87083b0cfe`; its implementation is the requested `d50776e4828078d86afc2a4f0e4f9532ed06f6e9` plus documentation commit `c3e94de`.

**1.1 — Bind lookup to the selected company and invitation surface, and withdraw lookup-derived form state when any bound input changes. (Blocking.)** The frozen contract binds the result and derived prefill to normalized email, selected company, deal, surface, and proposal fields (A5(b), A13, A14). `SmartLookupCard` accepts only `email` and `dealId`, keys only those values, and posts only those values (`src/components/onboarding/SmartLookupCard.tsx:54-70`); the route schema likewise has only `email` and `dealId` (`src/app/api/v1/invites/lookup/route.ts:62-66`). Consequently the `domain_mismatch` decision is made against any candidate-company domain rather than the selected company's verified domain, and changing the selected company cannot invalidate the result. Worse, although the card emits `null` while stale/loading/unavailable, `InviteModal` deliberately returns on `null` and leaves both lookup-derived phase and company unchanged (`InviteModal.tsx:357-373`). Track which values were applied by the current recommendation, include selected company and surface in the request/key, and synchronously withdraw only those derived values on every bound-input change without overwriting later user edits.

**1.2 — Derive the welcome brief's invitation action from live invitation authority. (Blocking.)** `computePerimeterInternal` sets `canInviteTeammate` to the role-name shortcut `subject.isExternal && companyRole === director` (`perimeter.ts:126-129`). Real `userCanInvite` additionally requires an external Director's own company to be a current party to this deal; other real authority branches also exist. A stale/anomalous seated Director can therefore see an action the send route refuses, violating C6/C8's live-authority rule. Build this capability through the real server-side invitation predicate for the current viewer/deal, fail closed on read failure, and test the party-removed negative as well as every permitted branch the brief is meant to expose.

Candidate-company derivation mirrors the material `userCanInvite` tiers, including delegated no-deal own-company `can_invite`, external-party confinement, internal deal authority, and A17's deal-membership branch. These correct parts do not cure findings 1.1 and 1.2.

## 3. Data lifecycle, rollback, flags, stale inputs, and audit semantics

The forward migration defaults/backfills phase 0, keeps old positional callers compatible through a final defaulted parameter, stores phase at send, and grants/audits that stored value at acceptance. The TS and PL/pgSQL feasibility logic agree on tenant coherence, actor authority, company-role coercion/Director authority, deal-role shape, party-derived role, and phase coercion. Nullable Boolean expressions in the write transaction are coalesced at the access guards; no remaining instance of the reported `NOT NULL` three-valued-logic bypass was found. Authority rows are locked before verdict derivation, and the fixed actor → company → deal → controlling membership → party order is sufficient for the inputs used by the verdict. The later email/domain locks do not invalidate that authority-race protection, although `prr-149.md` incorrectly says the authority block runs under an advisory lock already acquired: the email advisory lock is actually taken afterward (`invite_phase.sql:189-191`).

The rollback containment is one transaction and contends with `accept_invite` on the same invite row. Both interleavings are truthful: containment-first expires and audits only the returned pending row, while acceptance-first grants the confirmed phase and removes the row from containment. Operationally, the down script commits after dropping the 9-argument `create_invite` and only instructs the operator to re-run the prior migration afterward (`invite_phase_down.sql:52-57,147-153`), so rollback is not a standalone atomic restoration of service; restore the old RPC and grants inside the rollback transaction or make this downtime prerequisite explicit in release procedure and verification.

Flag-off route and surface checks are present, previews/lookups are read-only, and the document wall retains its load-bearing Internal → MNPI → external phase ordering (`documentAccess.ts:85-100`). The `DocumentSubject`/`DocumentViewer` split preserves semantic call sites; no grant/view/download bypass or document metadata expansion was found. Acceptance keeps the existing verification, credential, tenant, and row-lock sequence and only replaces literal phase 0 with the stored phase. No new secret-bearing response was found, and preview/lookup introduce no audit writes.

## 4. Edge cases and verification quality

**4.1 — Eliminate A19 timing/query-shape disclosure, and prove all three hidden-fact classes. (Blocking.)** Serialized bodies and warning order are flat and stable, but query execution depends on hidden facts. An existing user triggers one or two membership/authority reads that an unknown address does not (`lookup/route.ts:250-301`); a pending invite triggers `userCanManageInvite`, while absence does not (`lookup/route.ts:303-321`). An unauthorized caller can therefore distinguish existing-but-invisible user/seat/invite state through timing, which the task explicitly includes as an A19 channel. Use a constant query/authorization schedule independent of row existence (or an equivalently defensible construction) and add same-request measurements/assertions for hidden user, hidden seat, and hidden invitation. The current `lookup-indistinguishable.test.ts` covers only invisible users and byte/status equality, not seat, invitation, timing, or query schedule.

**4.2 — Supply the missing real D8 and rollback assertions; remove false evidence claims. (Blocking.)** The promised `invite-phase-rollback.test.ts` and `onboarding-e2e.test.ts` do not exist, so neither rollback/acceptance interleaving, old-caller rollback compatibility, nor automated D8.16 is covered. D8.4's same-request indistinguishability test omits hidden seats and invitations. `invite-modal-lookup.test.tsx` labels A14 withdrawal as covered but asserts only that the card becomes stale; it never asserts that a lookup-derived company and phase are withdrawn, and the shipped parent explicitly preserves them. This test passes for the wrong reason. The DB parity/acceptance suites are also skipped unless `RUN_DB_TESTS=1`; the acceptance probe verifies the verification gate but does not independently exercise the promised TOS/2FA sequence. Add the missing tests and wire the database/security probes into a reliable required gate.

The targeted reviewer run passed 86 tests across nine lookup/perimeter/welcome/flag/phase suites. GitHub's mandatory lint/typecheck/Vitest/build job passed. Those successes establish substantial coverage but do not compensate for assertions that omit the state they claim to protect.

## 5. Technical security, authorization parity, and delivery quality

The private perimeter boundary, fail-closed unknown-room decode, survivor-only document counts, proposal authorization ordering, actor-specific Director rule, delegated-candidate logic, TS/SQL parity, and rollback row-lock reasoning are sound as shipped. The invitation write transaction locks every mutable authority input used in its decision, coalesces nullable access expressions, and returns opaque mapped authorization/shape failures without partial invite, credential, delivery, or audit effects. The pre-existing catch-all route still exposes raw database messages on unrelated 500s; this PR does not broaden that behavior, but it remains a security debt.

**5.1 — Restore a green blocking dependency audit before approval. (Blocking delivery gate.)** GitHub Actions run `31264446325` failed `Dependency vulnerability audit`: production `nanoid <3.3.17` is high severity (`GHSA-2v37-7h3g-55p8`). A local `npm audit --omit=dev --audit-level=moderate` reproduces the failure. The lockfile is unchanged from `develop`, so the advisory is not introduced by this feature, but the PR cannot be approved while a required blocking check is red; update or otherwise resolve the audited dependency through the repository's dependency policy.

API/OpenAPI and flag constants are synchronized with the new routes and shipped behavior, and the demo runbook is clear as a manual path. The PR request overstates test evidence for rollback, A14, D8.4, and D8.16 and should be corrected after real coverage exists. Because the implementation changes document-access types and invitation RPC bodies, the missing database/concurrency evidence is material rather than advisory.
