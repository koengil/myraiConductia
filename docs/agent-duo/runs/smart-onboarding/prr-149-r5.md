## 1.3 — the company control now holds "unset"

The review was right, and my round-4 fix was the wrong half of it.

The select opened on the advisory bank, rendered it as chosen, and sent it to
preflight and to send. Round 4 hid that value from lookup only. That did stop
every counterparty address from contradicting a company nobody picked, but it
made the visible selection and the question disagree — A13 broken in a new
place rather than A5(b) repaired, exactly as `cr-prr-149-r4.md` says.

The actual defect was that "no company chosen yet" had no representation in the
control. It does now:

- `InviteModal.tsx:122` — an internal inviter starts with no company. An
  external one still has exactly one and no choice.
- `InviteModal.tsx:451` — a `Select a company` placeholder option, so unset
  is a state the control can display.
- `InviteModal.tsx:379` — `companyId={companyId || null}` passed straight
  through. The form asks about exactly what it shows. `companyTouched` returns
  to guarding the pre-fill, which is what it was for.
- `InviteModal.tsx:510` — the phase control appears with the company. An
  invitation with no company has no seat to phase.

Coverage in `tests/invite-modal-lookup.test.tsx:377-411`, asserting the request
body against the rendered value in both directions: the first lookup carries no
company because it necessarily precedes any pre-fill, the settled one carries
what the select then shows, and a manual change re-asks about the company the
inviter picked rather than the one the address matched. Mutation: restoring the
`options[0]` default failed the first test; reverted, 11 passed.

Side effect worth naming, because it retires an advisory item rather than
addressing it directly: `PerimeterPreview.tsx:49-108` already keys only when a
company exists, so with the company genuinely unset the empty-address proposal
previews stop firing. That is a consequence of the control being honest, not a
separate gate.

## 4.1 — tenant coherence in the predicate, honesty in the comment

Two parts, and the review is right that the second is the serious one.

**The dual-shape evaluation.** Both invitation shapes are still evaluated every
request with the real one selecting the answer, so the verdict is about the
invitation actually disclosed. What the review caught is that the comment above
it still claimed both arguments come from the request. They do not, and have not
since round 4. `lookup/route.ts:336-348` now states what the construction buys —
an identical response for an invisible invitation and an unknown address, and an
invocation count independent of whether a row was found — and what it does not:
a real deal whose MD is the actor returns earlier inside
`canManageDealMembersChecked` than a sentinel does, so a work difference
remains. Closing it means duplicating the policy or forcing a fixed query
schedule on every caller of a shared predicate. Recorded rather than papered
over. A19 as frozen is a property of the response ("the response contains no
field, flag, count, ordering, or wording..."), and that holds.

**The cross-tenant leak.** This one is real and predates the branch.
`userCanManageInvite` returned `true` for any firm admin before reading whose
tenant the invitation belonged to (`access.ts:416-438` as it stood), while
lookup finds pending invitations globally by normalized address. An admin is an
admin of a firm, not of the platform. `access.ts:416-441` now reads the invited
company's tenant and denies on mismatch, or on a company it cannot resolve.

Worth noting for the review: `canManageCompanyMembersChecked` and
`userIsDealMdChecked` already carry exactly this check (issues #116/#141); this
predicate was the one member of the family that never received it. Reading the
tenant ahead of the branch also removes the admin's short-circuit, so the admin
path no longer does visibly less work than every other path.

Fixtures had no `companies` row and no actor `tenant_id`, so the new read denied
two existing tests. `makeAdmin` (`tests/access-invites.test.ts:18-33`) now
supplies both by default, so a case expecting `false` fails on the rule it is
about rather than on tenant coherence. Two tests added
(`tests/access-invites.test.ts:192-221`): a same-tenant admin is allowed, a
cross-tenant one is not, and an invitation whose company cannot be resolved is
not disclosed. Mutation: dropping the tenant comparison failed both; reverted,
23 passed.

What is **not** added: the cross-tenant negative asserted end to end through the
lookup route. The predicate is the authority and it is covered directly; if the
review wants the route-level assertion as well, say so and it goes in.

## 3.1 — the walk carries the invitation, and ends with the second factor

The review is right that the store was too thin to prove what I claimed of it.
`{id, phase, verified}` meant `create_invite` discarded the address, company,
deal and both roles, and `accept_invite` answered from constants. The ending
could not disagree with the beginning because nothing connected them.

- `tests/onboarding-e2e.test.ts:120-170` — the store records what was actually
  sent, and acceptance answers from that record.
- `:369-378` — send is asserted against the invitation the MD composed on the
  form, not against a literal.
- `:394-400` — the invitee's company, seat and phase are read off the stored
  invitation, so a wrong invitation produces a wrong ending.
- `:450-467` — the missing leg. Acceptance runs at AAL1 by design: the invitee
  has proven an emailed code, not a device. The step that opens the full seat is
  the 2FA challenge, so the walk now calls the real
  `/api/v1/auth/mfa/complete` between acceptance and the perimeter and asserts
  the `MFA_CHALLENGED` audit row. D4 froze that flow as unchanged. It is
  unchanged; it is walked, not modified.

Mutations, all caught and reverted: sending the wrong company
(`route.ts:197`), sending the wrong seat (`route.ts:202`), and recording the
second factor as the wrong event (`mfa/complete/route.ts:29`). 2 passed.

The database half is still proven separately by
`supabase/tests/invite_phase_accept.sql`, and the two proofs are still not
joined by a migrated database in CI. That is the standing advisory item below,
not a claim.
