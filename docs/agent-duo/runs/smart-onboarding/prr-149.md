## What shipped

Three surfaces on the existing invitation flow. No third invitation path, no new
destination, no crawler or enrichment dependency, no autonomous grant.

1. **Smart lookup** (`POST /api/v1/invites/lookup`) on the Gate 0 Team step and
   the Team invite modal.
2. **Perimeter preview** (`POST /api/v1/invites/perimeter-preview`) under the
   invite form, in Gate 0, and in the member drawer for a proposed phase raise.
3. **Welcome brief** on the scoped external deal home after acceptance.

Plus the persistence the preview made necessary: the confirmed disclosure phase
now travels from the form to the granted seat.

## Implementation summary

### The seam (`M1`, `M2`, `M21`)

`DocumentSubject` (what a seat *is*) split from `DocumentViewer`
(`DocumentSubject & { userId }`). The predicates that gate real reads are
retyped to the subject, so they can be asked about a seat that does not exist
yet. Predicate bodies and check ordering are deliberately unchanged.

`src/lib/perimeter/perimeter.ts` keeps `computePerimeterInternal` unexported and
exposes three entry points, each constructing its own subject from its own
authorization (`assessProposal`, `userIsDealMd`, `getDocumentViewer`). No
exported function accepts a subject. The module has no `index.ts`: a barrel
could only re-export the core by making it importable.

`DocumentGate.room` narrowed to the `DocumentRoom` union with `parseDocumentRoom`
at the decode boundary. `userCanSeeDocument` only special-cases the internal
room, so an unrecognized value would fall through its walls and read as visible.
The DB `CHECK` makes such a row impossible; this keeps that a fact rather than an
assumption, without loosening the predicate.

`src/lib/api/v1/proposalFeasibility.ts` is the one shared feasibility path for
lookup, preview and send. Order is load-bearing: tenant coherence **first and
unconditional**, then `userCanInvite` as necessary-not-sufficient, then company
role, then deal-role shape, then phase bounds.

### The migration (`M20`)

`invites.phase int not null default 0 check (phase >= 0)`. `create_invite` gains
`p_phase int default 0` as a defaulted final argument (drop-and-recreate,
following the `20260804160000` precedent, grants re-issued). `accept_invite`
keeps its `(uuid, uuid)` signature and grants `v_invite.phase` instead of a
literal `0`, in both the seat insert and the grant audit.

`create_invite` re-derives authority and shape inside the write transaction,
reading authority rows `FOR SHARE` in one fixed order
(`users → companies → deals → deal_memberships → deal_parties`) under the
advisory lock it already took.

## Residual risks

1. **`RUN_DB_TESTS` is not set in CI.** The TS↔SQL parity probe runs locally
   only, so a green CI does not prove the two authority implementations agree.
   The command is documented in `api-v1.md`. Wiring it into CI is a real
   follow-up, deliberately not smuggled into this PR.
2. **Rollback is not lossless.** Pending invitations carrying a nonzero phase are
   expired and audited before the column drops. Recoverable via
   `audit_log detail->>'reason' = 'invite_phase_rollback'`.
3. **A NULL-logic bug existed in the SQL authority block** and was found by the
   probe, not by reading. `firm_role` is nullable, `null = 'admin'` is NULL, and
   `if not v_x then raise` does not fire on NULL. All derivations now coalesce to
   false. Worth a second pair of eyes on the same class of expression.
4. **Gate 0 lookup tests live in `tests/gate0-wizard-api.test.tsx`**, not the
   separate file `plan-v5 §12.1` named, to reuse ~200 lines of harness.
5. **The pre-existing catch-all 500** in the invites route still passes raw DB
   messages through. New exceptions are mapped ahead of it; the catch-all itself
   was left alone as out of scope.
6. **`--border` is referenced but undefined** in the external deal home.
   Pre-existing, untouched.

## Demo steps

`docs/03-engineering/onboarding-demo-runbook.md`, new section. Setup unchanged
(`platform_onboarding` on, `npm run db:migrate`).

1. Gate 0 Team step or Team invite: type a work email, see the card identify the
   company and propose a seat.
2. Change the proposed role or phase, watch "What they'll see" re-read.
3. **Scoping, not just the happy path:** as an external director, enter an
   address at another party's domain. No match, no warning.
4. Invite an external seat **at phase 2**, accept it. The seat lands on phase 2
   and the audit row records 2. Before this change it landed on 0.
5. Member drawer: preview what raising a member to phase 3 would release, before
   committing.
6. Open the deal home as the invitee: the brief names their seat, states what is
   available, offers only actions they can take.
