## 5. Technical security, authorization parity, and consistency

**5.1 — Put the pure core and all three trusted constructors in one module, or supply an enforceable import boundary. (Blocking; prior finding 5.1 remains open.)** The plan places `computePerimeterInternal(subject: DocumentSubject, ...)` in `src/lib/perimeter/perimeter.ts`, but places the three exported entry points in `src/lib/perimeter/index.ts` (`plan-v4.md:36-54`). In TypeScript, `index.ts` cannot call a function in another module unless that function is exported from `perimeter.ts`; once exported, any server caller can deep-import it and hand it a structurally forged `DocumentSubject`. The repository has no restricted-import/boundary rule that would make “not exported publicly” enforceable. Put the private core and three entry points in the same module with only the entry points exported, or define and test an equivalent compiler/lint-enforced boundary. Add an API/compile-time assertion that no subject-accepting perimeter function is importable while proposal, member-preview, and real-viewer paths remain usable.

(Blocking; prior finding 5.3 is only partially resolved.)** Section 7.1 restores the no-deal own-company `can_invite` row and §7.3 restores A17 branch (b), but the standalone algorithm and tests remain incomplete (`plan-v4.md:128-167`). Then add positive/negative tests for delegated own-company first-keystroke lookup, unrelated-company denial, external no-deal denial, external other-party denial, authorized deal-membership user disclosure, and the same normalized request with that hidden fact outside scope.
