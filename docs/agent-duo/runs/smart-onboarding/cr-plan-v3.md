# Review — plan-v3.md

## 1. Coverage of every frozen acceptance criterion

`plan-v3.md` is materially more complete than v2. Sections 2, 3, 6–10, and 13 restore the shared document policy, survivor-only counts, route ordering, response shapes, fail-closed reads, discriminated bound inputs, component behavior, flag parity, docs, demo, and mandatory gates. The criterion table names every A1–A19, B1–B13, C1–C11, and D1–D10 range, and the restored designs genuinely cover the preview and welcome contracts. The prior missing-plan finding 1.3 is therefore mostly resolved, but the map is not yet substantively complete.

**1.1 — Complete the operative behavior for A7 and D6 rather than merely naming their ranges. (Blocking.)** Section 7.2 derives `dealRole` only from `deal_parties.party_role` (`plan-v3.md:206`), which covers external seller/buyer companies but not the bank-company invitations in Gate 0 or Team. Gate 0 currently queues the creator's bank company and an internal role (`Gate0Wizard.tsx:615-638,868-883`), while frozen Q4 requires a context-appropriate bank-side internal recommendation as well as party-derived external recommendations (`spec-v2.md:247`). Define the deterministic internal recommendation and reason, its prefill/override behavior, and tests on both surfaces. Separately, the criterion map maps D6 to “Gate 0 boundary, no third flow” (`plan-v3.md:333`), but frozen D6 is the Conductia voice and visible-copy contract, including the no-em-dash rule (`spec-v2.md:199`). Assign that contract to the three components/runbook and to an assertion or review gate that checks the actual visible strings. The A1 map should also name the real integration sites M11 and M12, not only M4/M5/M8; that correction is required as part of this blocker, not a separate design change.

## 2. Scope and reuse of approved surfaces

The route and UI footprint remains within the frozen experience: Gate 0, Team invite, Member Drawer, the existing external deal home, shared document/destination predicates, current preflight, and the existing send/accept lifecycle. There is no chatbot, external enrichment, automatic grant, third invitation path, persisted preview, new destination, or task system. Persisting a confirmed phase is the minimum state required by A9/B2 and is explicitly allowed by Q12.

**2.1 — Remove the silent frozen-authority change that coerces every external-company invitee to Member. (Blocking; frozen-spec escalation.)** Sections 5.1 and 5.3 say an “external invitee” is always coerced to `company_role: member` (`plan-v3.md:118,141`). Current behavior only locks an **external inviter** to Member; an authorized internal inviter can explicitly choose Director (`InviteModal.tsx:145-149,383-396`), and the send route permits it when `canManageCompanyMembers` holds (`invites/route.ts:130-145`). Frozen A9 says the inviter can override company role, Q5 says Director remains an explicit choice, and the out-of-scope boundary forbids changing who may invite (`spec-v2.md:113,249,232-234`). Preserve the current actor-specific rule in `assessProposal` and SQL: external directors may add own-company Members only, delegated `can_invite` Members may not create Directors, while an actor with existing company-management authority may explicitly invite a Director. Add positive and negative TS/RPC parity cases for those distinctions. This is a silent spec change, not an advisory wording issue.

## 3. Data lifecycle, rollback, flags, stale inputs, and audit semantics

The forward phase migration is otherwise credible. A final defaulted argument preserves old callers, `default 0` backfills existing rows, the exact RPC signature and grants are recreated, internal invitations remain phase 0, and `accept_invite` grants and audits the stored phase. Sections 8, 9, and 11 correctly define opaque failures, response supersession, feature-flag order, and flag-off UI parity.

**3.1 — Make rollback containment atomic with acceptance and audit only rows actually contained. (Blocking.)** Section 4.3 correctly admits that dropping a confirmed nonzero pending phase is destructive, but its “select; set expired; audit” sequence (`plan-v3.md:91-100`) does not state a transactional row-lock or conditional-returning boundary. `accept_invite` locks the invite row `FOR UPDATE` before checking `status` (`20260804160000_invite_safeguard_2fa.sql:673-695`), so rollback must contend on that same row. Specify one migration transaction using an atomic `UPDATE ... WHERE status='pending' AND phase>0 ... RETURNING` (or an equivalent `FOR UPDATE` protocol), create withdrawal audit rows only from the rows actually expired, and revert the RPC/column only after that containment commits. Test both interleavings: containment wins and acceptance fails without a grant, or acceptance wins and the already-granted phase remains truthful. This closes prior 3.3 without inventing a silent phase-0 fallback.

## 4. Edge cases and verification quality

Section 12.1 now assigns real parent/API/component suites to all sixteen D8 obligations, including same-request alternate-state indistinguishability, both invitation surfaces, member target races, preview leakage/parity/failure/zero states, welcome archetypes and later visits, every flag surface, and the seeded E2E path. The migration and write-race suites are also useful. Prior 4.1 is nevertheless only partially resolved.

**4.1 — Finish concrete ownership for the full D3/D4/Box/audit contract. (Blocking.)** Section 12.3 gives files, but its assertions are narrower than the frozen and previously requested invariants. `onboarding-no-secrets` names only serialized success payloads, not opaque error responses. `onboarding-audit-neutral` preserves send/accept/grant/view/download but omits the explicitly frozen phase-change event (`spec-v2.md:153`). The D4 row in §13 points only to perimeter purity/fail-closed reads (`plan-v3.md:331`) and provides no fixture/assertion that the modified accept RPC leaves verification, TOS, and 2FA boundaries unchanged. `onboarding-storage-nonregression` proves the new reads never call storage, but “Box and Supabase-bucket paths unchanged” is a conclusion, not the requested success/unavailable/compensation/fallback regression evidence for the shared upload predicate refactor. Add explicit error-response secret assertions; phase-change audit assertions; acceptance fixtures proving verification/TOS/2FA sequencing survives the RPC change; and named existing or new Box/bucket success, unavailable, and compensation/fallback suites with expected assertions. Keep D6 visible-copy verification from 1.1 in this mandatory set.

## 5. Technical security, authorization parity, and consistency

The document-wall direction remains correct: `DocumentRoom` is decoded before policy evaluation, unexpected values make the whole result unavailable, and the real Internal → MNPI → phase check order is unchanged. Prospective tenant coherence precedes `userCanInvite`; member preview reuses `userIsDealMd`; the lookup warning schema is fixed and metadata-free; and document queries project only policy fields.

**5.1 — Give proposal, member, and real-viewer perimeter calls distinct trusted construction paths. (Blocking.)** The private unique-symbol brand does prevent ordinary external structural construction, resolving the narrow type-forging concern. But `computePerimeter` accepts only `AuthorizedSubject`, and the plan says that type is constructible only inside `proposalFeasibility.ts` (`plan-v3.md:121-130`). Member phase preview is authorized by `userIsDealMd`, not `assessProposal` (`plan-v3.md:160-162`), and the welcome uses the real membership-validated viewer (`plan-v3.md:261-265`); neither can legally construct the only accepted input. Define separate opaque proposal/member/current-viewer subjects or keep the pure core private behind three server entry points, each with its own authorization/membership constructor. Add compile-time/API tests proving proposal callers cannot forge a subject while member and welcome paths remain usable. As written, B11 and C1–C11 cannot be implemented through the declared API.

**5.2 — Lock or atomically condition on every mutable authorization row, and compare the full TS and SQL decision rather than only `userCanInvite`. (Blocking.)** Moving checks into `create_invite` closes the route-to-RPC gap only if those checks remain true through the insert. The existing advisory lock is keyed to email and serializes competing sends (`invite_safeguard_2fa.sql:381-405`); it does not serialize revocation of actor privileges, deal membership/access scope, company type, or `deal_parties`. Section 5.3 merely loads those rows (`plan-v3.md:136-146`) and names no `FOR SHARE`/`FOR UPDATE`, matching advisory lock, version predicate, or single conditional write, so a concurrent revocation can commit after a read and before the invite insert. Specify the exact PL/pgSQL lock/conditional order for actor, company, deal, controlling membership/access-scope, and party rows, and test paused/interleaved revocation transactions, not only state changes completed before RPC entry. Also compare `assessProposal`'s **full** tenant/authority/company-role/company-type/deal-role/party-role/phase verdict against SQL. A test that compares only `userCanInvite` to the transaction cannot detect shape divergence because that helper deliberately excludes shape, and it would bless the incorrect Director coercion in 2.1.

**5.3 — Restore the missing invitation/disclosure branches in lookup scoping. (Blocking.)** Section 7.1's no-deal internal candidate rule lists only director/admin-managed companies (`plan-v3.md:191-197`), but current `userCanInvite` also permits a delegated internal Member with `can_invite` to invite into their own company when no deal is attached (`access.ts:330-337`). Include that own-company candidate and a positive first-keystroke test, while retaining the negative unrelated-company cases. Section 7.3's `existing_user` rule permits only same-company or in-tenant overseer disclosure (`plan-v3.md:210-216`), silently omitting frozen A17's third branch: an actor authorized over a deal membership on which that user holds a seat (`spec-v2.md:129`). Include that authorized deal-membership branch, keep explicit tenant equality and bare-fact response shaping, and test both its positive case and an unauthorized same-request alternate state.

## Decision

`changes_requested`. Findings **1.1, 2.1, 3.1, 4.1, 5.1, 5.2, and 5.3 are all genuinely blocking** because they leave frozen behavior unmapped, silently narrow existing/frozen Director authority, permit rollback or send-time races, leave mandatory cross-cutting invariants unproved, or make required consumers impossible. **There are no advisory-only findings.** Because this is the third substantive plan round, this decision requires the run's documented terminal escalation rather than another ordinary plan revision. The escalation should carry these exact blockers and preserve the already-correct parts of v3: shared document policy/check ordering, phase carry, fail-closed reads, bound inputs, flag parity, D8.1–D8.16 ownership, deterministic demo, and synchronized docs/gates.
