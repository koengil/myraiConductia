# Demo-day switch checklist (Oct 30, #173)

What to turn on for the demo tenant, in what order, and how to roll each step back. Per the owner's 2026-10-25 decisions:

- The primary demo tenant is a new Google Workspace for synthetic test mail only. It is approved, and the release co-owner is configuring it.
- M365 is the backup ([Backup: M365](#backup-m365) below).
- There is no Ignatious connection yet. The steps below are the same for the Ignatious tenant when it connects, with that tenant's ids.
- The code freeze is the end of Oct 28. The promotion date is being set by the owner, the release co-owner and the team. This checklist assumes no date.

Rules for every step:

- **Owner** marks a step only the owner approves or runs. **Hosted** marks a step that changes a hosted system (Vercel, hosted Supabase, AWS, a Google Workspace or an M365 tenant). Agents run neither. They write the exact steps, as below.
- **Schema** reaches a hosted database only through a reviewed migration and the Migrate database Action, never through the SQL editor. The operational data writes the runbooks prescribe are owner-run, and are marked **Owner, hosted data write, per** the runbook section that gives the command. Each needs the owner's explicit go-ahead at the time it runs. `feature_flags` rows are flipped one by one, never with `scripts/enable-flags.ts`, which refuses `NEXT_PUBLIC_APP_ENV=prod` ([production bootstrap §4](./production-bootstrap.md#4-feature-flags)).
- `feature_flags` has no tenant column: a flag is on for every tenant of that database. The per-tenant gates are the `discovery_tenant_approvals` rows and the verified tenant list.
- No live model call runs before the owner's go-ahead and key handling. There is no separate ZDR probe (#787). The first live AI calls are the real worker on the synthetic test tenants, through the model gateway module (`src/lib/modelGateway/`), which enforces zero data retention on every call.
- Turn things on in this order, and roll them back in the reverse order.
